# Regole Git e Commit

> Versione 1.6 — ultima revisione: 2026-11-12.

> Richiede `core.md`. Si importa in ogni progetto versionato con git; `core.md` §5c rimanda a questo modulo.

**Ambito di Claude: solo commit locali; con le skill il lancio è il via libera, fuori dalle skill serve l'ok esplicito.** Con `/kit:commit-passo` (e `/kit:pr-develop`, `/kit:pr-main` per le PR) il lancio da parte dell'utente vale come via libera: la skill crea i commit senza altre conferme (vedi «Skill del plugin `kit`»). Fuori dalle skill Claude non committa mai di propria iniziativa, nemmeno un commit singolo: prima di ogni commit mostra file inclusi e messaggio proposto e **attende l'ok esplicito dell'utente**; senza ok, non committa. Il branch locale di lavoro Claude lo crea liberamente, senza conferma, quando lo ritiene opportuno per gestirvi i commit. I commit seguono queste linee guida, al termine di ogni unità logica di lavoro che builda e ha i test verdi. Push, tag, PR, rilasci e pipeline sono operazioni verso l'esterno e seguono la sezione «Integrazione GitHub» (i file di pipeline può scriverli e committarli Claude, vedi `core.md` §5). A fine lavoro Claude segnala che i commit sono pronti per il push.

## Integrazione GitHub: operazioni consentite e GitHub CLI
- **Consentite sempre:** `push` normale, creazione di tag (alle condizioni di «Rilascio»: nome `X.Y.Z` e branch `main`), PR e rilasci non richiedono un'approvazione per progetto. Claude li esegue solo su richiesta dell'utente (lanciare `/kit:pr-develop` o `/kit:pr-main` è la richiesta della PR) o con sua conferma esplicita; per tag, push del tag e rilascio propone lui l'operazione e chiede il via (vedi «Rilascio»).
- **Una sola domanda per progetto: la GitHub CLI.** Alla prima operazione che passa da `gh` (PR o rilascio) in un progetto, Claude chiede **una sola domanda**: se su questo PC è installata la GitHub CLI (`gh`). Con la risposta scrive nel `CLAUDE.md` di progetto, nella sezione «Eccezioni alle regole globali», la riga fissa `- **GitHub CLI (gh) installata:** sì/no (AAAA-MM-GG)`. Da lì in poi non la chiede più, salvo cambi di ambiente.
- **Con `sì`:** PR e rilasci passano da `gh`. Prima, Claude verifica con `gh auth status` (sola lettura) che sia autenticata; se non lo è, lo dice e non procede.
- **Con `no`, o riga assente o non valida:** Claude non propone né esegue PR e rilasci, e indica all'utente cosa fare. Il hook `guard-commands` blocca `gh pr` e `gh release` finché la riga non c'è o dice `sì`.
- **Push e tag** usano git e restano consentiti anche con `no` (il tag alle condizioni di «Rilascio»).
- **Uso di `gh`:** solo per l'operazione richiesta (PR o rilascio), senza altri usi (né lettura di stato, CI o PR), salvo la verifica di autenticazione. Il merge di PR e le chiusure di git flow restano a cura dell'utente (vedi «Branch»).
- **Pipeline (`gh workflow run` e simili):** Claude può avviarle, ma non senza una domanda esplicita di conferma **prima di ogni esecuzione**. La domanda nomina la pipeline, il branch o il ref e gli input; senza un sì a quella domanda Claude non avvia nulla. La conferma vale solo per quella esecuzione. Il hook non le blocca: la regola è questa.
- **Sempre bloccati:** restano vietati `push --force` (e varianti), `reset --hard`, `--no-verify`, `clean -f`, e `rm -rf`: riscrivono la storia, saltano i controlli o cancellano dati. Il hook `guard-commands` del plugin `kit` applica questo elenco. La cancellazione di branch remoti (`git push --delete`) è bloccata dall'hook salvo per i branch di lavoro (`feature/`, `bugfix/`, `release/`, `hotfix/`), con la conferma dell'utente che resta una regola scritta (vedi «Branch»). `git init` resta vietato a Claude (vedi «Repository, fine riga e hook») ma come regola scritta, non più bloccato dall'hook; lo stesso vale per maiuscola iniziale, punto finale e lunghezza massima dell'oggetto del commit (l'hook controlla solo `tipo(scope): descrizione`).

## Branch (git flow)
- **Modello:** git flow completo, **obbligatorio in ogni progetto**. `main` contiene solo codice rilasciato; `develop` è il branch di integrazione (il nome è sempre `develop`); il lavoro nasce su branch dedicati: `feature/` (nuove funzionalità), `bugfix/` (correzioni), `release/` (preparazione di un rilascio), che partono da `develop`, e `hotfix/` (correzione urgente su produzione), che parte da `main`. Non esiste un flusso semplificato senza `develop`: si deroga solo con approvazione esplicita dell'utente.
- **Se `develop` non esiste:** Claude non propone di partire da `main` e non lo aggira. Pone una sola domanda: se può creare `develop` da `main` (branch locale, solo dopo la conferma; `push` e collegamento al remoto restano all'utente). Ricevuta la risposta, crea il branch di lavoro (per esempio `feature/nome-breve`) a partire da `develop`, senza altre conferme. Se il progetto ha un branch principale con altro nome (per esempio `master`) o un altro modello, Claude lo segnala e chiede se adottare `main` e `develop`, senza rinominare nulla di sua iniziativa.
- **Nomi:** `tipo/descrizione-breve` in minuscolo con trattini (`feature/order-export`, `bugfix/login-redirect`, `release/1.4.0`, `hotfix/1.4.1`). Se il lavoro è collegato a un ticket, il suo ID entra nel nome (`feature/ABC-123-order-export`). I commit dentro il branch usano i tipi Conventional Commits (`feat`, `fix`, ...), indipendenti dal nome del branch.
- **Branch di lavoro, senza conferma:** prima del primo commit di un lavoro Claude dice in una riga su quale branch si trova; se è su `main` o `develop` sceglie tipo, nome e branch di partenza e crea il branch di lavoro da solo, quando lo ritiene opportuno per gestirvi i commit. Se è già su un branch di lavoro, continua lì. Non serve chiedere conferma.
- **Mai commit diretto su `main` o `develop`.** Un'eccezione esiste solo se l'utente la dichiara esplicitamente e vale per il caso o il progetto indicato, non diventa la regola generale.
- Claude crea il branch locale di lavoro senza chiedere conferma. Non esegue le chiusure di git flow (merge di `feature`, `release`, `hotfix` in `develop`/`main`): sono a cura dell'utente. **Eccezione, solo con `/kit:pr-main`:** dopo che l'utente ha confermato il merge su `main` (domanda ogni volta), la skill può cancellare i branch di lavoro (`feature/`, `bugfix/`, `release/`, `hotfix/`) locali e remoti già uniti, solo quelli che l'utente conferma, e allinea `main` e `develop` locali con `git pull --ff-only`, senza merge né rebase né commit; mai `main` o `develop`. Un branch remoto nasce solo dal `push` normale del branch di lavoro (necessario per aprire una PR), eseguito su richiesta o con conferma. Il tag è consentito alle condizioni di «Rilascio».
- **Base avanzata o conflitti:** se Claude nota che il branch di partenza è avanzato, o che ci sono conflitti (per esempio dopo un'operazione dell'utente), lo segnala e non committa finché i conflitti non sono risolti. Può **proporre** come risolverli, mostrando le versioni a confronto e il motivo della scelta, ma applica la risoluzione solo dopo l'ok dell'utente; l'aggiornamento del branch (merge o rebase) resta a cura dell'utente.
- Branch di breve durata. L'aggiornamento dal branch di partenza e il merge (squash o rebase secondo la politica del progetto) sono a cura dell'utente; il push è consentito su richiesta o con conferma (vedi «Integrazione GitHub»). Con git flow la politica ha una regola fissa, vedi "Pull Request": squash solo per le PR verso `develop`, merge commit per ogni PR che coinvolge `main`.

## Messaggi di commit (Conventional Commits, in inglese)
▲ Verificato dal plugin `kit` (hook `guard-commands`): un messaggio non conforme viene bloccato.
- Formato: `tipo(scope): descrizione` — tipi ammessi: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`, `revert`.
- Oggetto all'imperativo, minuscolo, senza punto finale, al massimo 72 caratteri. `scope` opzionale (modulo o slice, es. `orders`, `auth`).
- Il corpo, se serve, spiega il **perché** e non il cosa, andando a capo a 100 caratteri circa.
- Breaking change: `!` dopo il tipo/scope (`feat(api)!: ...`) e footer `BREAKING CHANGE: ...`. Riferimenti ai ticket nel footer (`Refs: ABC-123`).
- **Il corpo è la norma, non l'eccezione**, per tutto ciò che non è banale: un breve paragrafo che spiega perché si cambia e quale problema risolve (causa radice per i `fix`), oppure un elenco puntato (`- `) degli interventi principali. Cita per nome tipi, metodi e file toccati.
- Riferimento a issue o PR nel corpo o nell'oggetto: `(issue #123)`, `(#456)`. Su `develop` i commit di squash di una PR hanno il suffisso `(#NNN)`; su `main` il commit di merge ha oggetto `merge: <sintesi> (#NNN)` (vedi «Pull Request»).
- **Bot delle dipendenze (Dependabot/Renovate):** quando Claude scrive la configurazione del bot, i commit e i titoli delle PR usano il prefisso `build(deps)` per le dipendenze di produzione e `chore(deps-dev)` per quelle di sviluppo, così restano conformi a Conventional Commits e al lint sulle PR verso `develop`.
- Mai messaggi generici (`Save uncommitted changes`, `wip`, `fix`, `update`): ogni commit dice cosa e perché. Unica eccezione, i commit WIP richiesti dall'utente (vedi "Repository, fine riga e hook").
- Trailer in fondo, dopo una riga vuota. Se è richiesta un'attribuzione a Claude: `Co-Authored-By: <modello> <noreply@anthropic.com>`; se la sessione ha un link, anche `Claude-Session: <url>`. Mai nell'oggetto.

## Granularità e sequenza
Una funzionalità non è un unico commit gigante: è una **serie di commit piccoli e ordinati sul branch**, ciascuno che builda e passa i test. Ordine tipico:
1. `feat(scope)`: modello/entità, configurazione EF e migrazione (+ servizio applicativo, se piccolo);
2. `feat(scope)`: endpoint o UI che usano il servizio;
3. `test(scope)`: test del servizio e dell'isolamento tra utenti; test di integrazione per ciò che gli unit test non coprono, nel progetto `IntegrationTests` con il database di prova (vedi `core.md` §4 e `backend-app.md` §4.5);
4. `docs(scope)` / `chore(...)`: aggiornamento di `README.md` e `CHANGELOG.md` (a ogni step del piano, vedi `core.md` §5b), ADR se servono.
- I **test stanno in commit `test(scope)` separati** dal codice di produzione, ma nella stessa PR; mai una PR con funzionalità senza test.
- Un `fix` è un commit a sé, con la causa radice nel corpo. Un bug di sicurezza usa `fix(security)`.
- Non mescolare refactoring, formattazione e cambi di comportamento nello stesso commit.
- Le chiavi di traduzione IT/EN viaggiano con la superficie UI che le usa (un commit per superficie va bene, come `extract orders surface strings`).
- Se un commit corregge il precedente della stessa serie e non è stato ancora pubblicato (nessun upstream che lo contiene), puoi fare `--amend` solo sull'ultimo commit creato da te in sessione; altrimenti crea un commit `fix` nuovo.

## Commit multipli: piano e passo-passo
**Con `/kit:commit-passo`** il lancio è il via libera: la skill presenta il piano, crea tutti i commit in sequenza senza ok a ciascuno né pause, e si ferma con una domanda solo se un controllo fallisce, compare un possibile segreto, il tipo del commit è ambiguo, un file ha modifiche per commit diversi, la build o i test sono rossi o un hook fallisce. Il resto di questa sezione descrive il flusso **fuori dalle skill**: quando le modifiche da committare sono più di un'unità logica (o l'utente chiede "committa tutto"), Claude non crea i commit in blocco:
1. **Piano:** prima di creare qualsiasi commit, elenca i commit che intende fare, numerati e in ordine (vedi "Granularità e sequenza"): per ognuno oggetto proposto e file inclusi. Segnala i file che non rientrano in nessun commit (segreti, generati, estranei al lavoro). Segnala anche i file con **modifiche destinate a commit diversi**: `git add -p` è interattivo e non disponibile, quindi per quei file Claude **chiede caso per caso** se spezzarli (preparando una patch parziale applicata con `git apply --cached`, mostrata prima di committare) oppure unire i commit interessati; non sceglie da solo. Il piano si può correggere: l'utente può unire, dividere, riordinare o escludere commit. Il piano dei commit si salva in un file dedicato, **`piano-commit.md`** nella root del progetto (distinto da `PIANO.md`, che resta il piano di sviluppo): una casella di stato per commit, aggiornata dopo ognuno, così non si perde in un lavoro lungo o tra sessioni; come `PIANO.md`, non si committa se l'utente non lo chiede e, finiti tutti i commit del piano (caselle tutte spuntate), si cancella senza chiedere conferma.
2. **Un commit alla volta:** dopo l'approvazione del piano crea **solo il commit n. 1** (file aggiunti per nome, `git status` e `git diff --staged` controllati, regole di messaggio e hook come sopra) e mostra hash e oggetto.
3. **Pausa e conferma:** dopo ogni commit si ferma e chiede se procedere con il successivo, indicando quale sarà (`n/N`, oggetto). Procede solo dopo il via dell'utente; se l'utente cambia idea sul piano, lo aggiorna e ripresenta l'elenco residuo.
4. **Nessun via anticipato:** l'approvazione del piano non vale come approvazione di tutti i commit, e il "sì" a un commit non vale per i successivi. Un'eccezione ("fai tutti i commit di fila") vale solo per quel piano, se l'utente la dichiara esplicitamente; lanciare `/kit:commit-passo` è una dichiarazione di questo tipo.
5. **Chiusura:** finiti i commit (o interrotti dall'utente) riepiloga quelli creati e quelli rimasti, e segnala che i commit sono pronti per il `push` (che Claude esegue solo su richiesta o con conferma). Poiché ogni commit è stato verificato prima di crearlo, si può fare `push` a lotti, anche intermedi, senza aspettare la fine della serie. Nel riepilogo (e nelle pause, se la serie è lunga) Claude **propone i punti sensati per un push intermedio**: dopo un gruppo di commit coerente (es. una funzionalità completa con i suoi test), con build e test verdi fino a lì. Resta una proposta: il push parte solo su richiesta o con conferma.
6. **Se un commit fallisce** (hook, test rossi): corregge la causa, ricrea quel commit e ripresenta il punto del piano; non passa al successivo.

## Cosa non entra mai nel repository
- Segreti, `.env`, certificati, chiavi, dump di database, file generati (`bin`, `obj`, `node_modules`, `dist`) e file di IDE personali. Verifica `.gitignore` all'inizio del progetto.
- Prima di ogni commit controlla `git status` e `git diff --staged`: aggiungi i file per nome, mai `git add -A` alla cieca (▲ verificato da `guard-commands`: blocca `git add -A`, `git add .` e i file sensibili). Se compare qualcosa che sembra un segreto, fermati e segnalalo.
- **Controlli automatici sulle modifiche in stage:** `git diff --cached --check` (spazi finali, marcatori di conflitto, fine riga misti); `gitleaks` solo se è già installato sulla macchina (altrimenti lo dici, senza installarlo); segnala file aggiunti molto grandi o binari non attesi prima di committarli.
- I lock file (`packages.lock.json`, `package-lock.json`) vanno committati; i file di build no.

## Repository, fine riga e hook
- **Cartella non versionata:** se la cartella di lavoro non è un repository git, Claude **non esegue mai `git init`**, nemmeno se l'utente non lo vieta: si limita a **segnalare** che in quel progetto/soluzione git non è stato inizializzato e non committa. Claude è limitato ai commit locali su repository già esistenti; l'inizializzazione (e il collegamento a un remoto) è a cura dell'utente. Quando l'utente avrà inizializzato il repository, Claude riprende da lì.
- **Fine riga:** il repository ha un `.gitattributes` con `* text=auto` e `eol` esplicito per i file che lo richiedono (es. `*.sh text eol=lf`, `*.ps1 text eol=crlf`); `.editorconfig` coerente. Serve perché si lavora su Windows: senza, i diff si riempiono di cambi di fine riga. Se manca, Claude lo segnala e **valuta caso per caso** se proporlo: non lo dà per scontato e non lo crea né lo committa senza il tuo ok. Se l'utente conferma, il commit è `chore(repo)` a sé, e solo se il repository esiste (Claude non lo inizializza, vedi sopra). In un progetto esistente la modifica delle regole di fine riga può cambiare molti file: va valutata con l'utente prima di toccarli.
- **Hook pre-commit** (es. husky + lint-staged, o hook in `.githooks/`): sono parte del progetto. Claude può scriverli e committarli se richiesto; l'attivazione sulla macchina (`core.hooksPath`, `npm install`) è dell'utente. Se un hook fallisce durante un commit, Claude corregge la causa e ricrea il commit (divieto di `--no-verify`: vedi «Sicurezza della cronologia»).
- **Commit con test rossi (WIP):** di norma ogni commit builda e passa i test. Un commit con build o test rossi è ammesso solo se l'utente lo chiede esplicitamente (es. per salvare un lavoro a metà); in tal caso oggetto `chore(wip): <cosa è in corso>`, corpo che indica cosa è rotto e perché, e nessun `--amend` o riscrittura successiva senza richiesta. La pulizia (squash) prima della PR è dell'utente.

## Sicurezza della cronologia
- Mai riscrivere cronologia che potrebbe essere già pubblicata (`rebase`, `reset`, `commit --amend` su commit non creati da te in sessione) senza conferma. Mai `push --force` (né `--force-with-lease`).- Mai saltare gli hook (`--no-verify`) né la firma dei commit: se un hook fallisce, correggi la causa.
- Per annullare una modifica già pubblicata usa `git revert`, non `reset`.
- Se un segreto finisce in un commit, la rotazione del segreto viene prima di qualsiasi pulizia della cronologia.

## Pull Request (apertura con la skill o su conferma, merge a cura dell'utente)
Claude apre PR con `gh` solo se la GitHub CLI è installata sul PC, come registrato nel `CLAUDE.md` (vedi «Integrazione GitHub»), lanciando `/kit:pr-develop` o `/kit:pr-main` (il lancio è il via libera) oppure su richiesta o conferma esplicita fuori dalle skill. In ogni caso struttura i commit perché la PR sia pulita e, solo se l'utente lo chiede, redige titolo e descrizione da incollare.
- Una PR per issue o funzionalità, con titolo Conventional Commits; la serie di commit sul branch resta leggibile (nessun commit di "pulizia" in coda).
- La descrizione riporta: cosa cambia e perché, come è stato testato, impatti (migrazioni, variabili d'ambiente, breaking change), riferimento all'issue (`Closes #N`) e, per la UI, screenshot o note sui temi/lingue verificati.
- Il commit di merge (se il progetto non usa squash) ha oggetto `merge: <sintesi> (#NNN)` e un corpo che riassume l'insieme della funzionalità, con eventuali garanzie importanti (es. sicurezza, dati salvati, comportamento di default).
- La PR deve rispettare la checklist di consegna (`core.md` §0b) e avere la CI verde prima della richiesta di review (a cura dell'utente: Claude non legge lo stato della CI, vedi «Integrazione GitHub»).
- **Strategia di merge con git flow (a cura dell'utente):**
  - `feature/*` e `bugfix/*` verso `develop`: **squash**. Il titolo della PR diventa l'oggetto del commit, quindi segue Conventional Commits.
  - Ogni PR che coinvolge `main` (`develop` → `main`, `release/*` → `main`, `hotfix/*` → `main`) e il ritorno di `main` in `develop`: **merge commit**, mai squash né rebase. Lo squash scarta la storia dei commit: dopo uno squash di `develop` in `main` le due linee non hanno più un antenato comune aggiornato e la PR successiva va in conflitto (`add/add`) su tutti i file già portati.
  - Se `main` contiene commit che `develop` non ha (per esempio dopo un hotfix, o uno squash già avvenuto), prima di aprire la PR verso `main` si porta `main` in `develop` con un merge commit, risolvendo gli eventuali conflitti a favore di `develop` quando il contenuto di `main` è una versione più vecchia. Quel merge si fa su un branch dedicato (`bugfix/sync-main-into-develop`; se il nome esiste già, per una sincronizzazione precedente, si propone con conferma il primo nome libero `-2`, `-3`, ..., senza cancellare né riusare il vecchio) con PR verso `develop` chiusa **con merge commit**: con lo squash il conflitto tornerebbe.
  - Il controllo dei commit della PR (lint Conventional Commits) si esegue solo sulle PR verso `develop`. Su una PR verso `main` l'intervallo contiene i commit di squash già in `develop`, il cui oggetto è stato controllato (o no) quando erano PR; rieseguirlo li farebbe fallire per motivi estranei alla PR.

## Rilascio
- Versionamento SemVer. La versione vive in un solo punto (es. `Directory.Build.props`) ed è accompagnata da una voce di rilascio in `CHANGELOG.md` (le voci dei singoli interventi sono già state scritte step by step). La sottosezione `### Rilascio X.Y.Z` raggruppa i punti salienti per categoria, in italiano, con etichette in grassetto in quest'ordine e solo quelle che servono: **Aggiunto:** (funzioni nuove), **Modificato:** (cambi di comportamento o di configurazione), **Corretto:** (fix), **Sicurezza:** (correzioni di sicurezza). Le categorie sono etichette in grassetto dentro la sottosezione, non titoli `###`, perché i titoli `###` sono già usati per i singoli interventi.
- Il rilascio è un commit dedicato e isolato dalle funzionalità: `chore(release): bump version to X.Y.Z`, con corpo a elenco (file di versione aggiornato, voce di rilascio aggiunta al changelog, fix inclusi). Per un fix urgente può essere nell'oggetto: `fix(scope): ... and release X.Y.Z`.
- **Formato del tag:** `X.Y.Z`, senza prefisso `v`, identico alla versione nel file di versione e nella voce `### Rilascio X.Y.Z` del `CHANGELOG.md`. Tag annotato (`git tag -a X.Y.Z -m "..."`).
- **Momento del tag:** solo **dopo** il merge su `main` della PR `release/*` o `hotfix/*` (o `develop` → `main`), fatto dall'utente. Il tag punta al commit di merge su `main`, mai a un commit di un branch di lavoro o di `develop`, così non finisce su codice non rilasciato. Claude verifica che il merge sia su `main` e che versione e `CHANGELOG.md` coincidano con il tag, poi **chiede il via dell'utente prima di creare il tag**, anche se l'utente non l'ha richiesto: la domanda nomina il tag e il commit di merge a cui punta, e senza un sì non crea nulla. Il via vale solo per quel tag. Anche per il `push` del tag Claude chiede conferma, senza bisogno di una richiesta esplicita dell'utente. Il rilascio con `gh release` viene dopo il tag (già pubblicato con il push): Claude lo propone di sua iniziativa e **chiede il via prima di crearlo**, senza bisogno di una richiesta esplicita; la domanda nomina tag, titolo e note (dalla voce `### Rilascio X.Y.Z` del `CHANGELOG.md`), e senza un sì non crea nulla. Restano il requisito della GitHub CLI installata e autenticata e la conferma separata per ogni pipeline.
- **Commit di bump, proposto di iniziativa:** a fine di ogni piano concluso (tutte le caselle spuntate, verifiche fatte; `core.md` §6.15) Claude valuta se le modifiche giustificano un rilascio e, se sì, **propone il commit di bump senza attendere una richiesta esplicita**: versione proposta con il motivo (SemVer: `feat` minor, `fix` patch, breaking change major), file di versione e voce `### Rilascio X.Y.Z` del `CHANGELOG.md`. Se non lo ritiene giustificato, lo dice in una riga. Vale la regola dei commit: nessun commit senza l'ok esplicito dell'utente, e mai su `main` o `develop` (il bump si fa su un branch `release/X.Y.Z`, o `hotfix/X.Y.Z` da `main`, confermato come da «Conferma del branch»). Claude non decide la versione da solo: la propone e attende il sì.
- Claude prepara il commit di bump solo come sopra. Il tag è consentito alle condizioni sopra (vedi «Integrazione GitHub»). ▲ L'hook `guard-commands` blocca la creazione di un tag con nome diverso da `X.Y.Z` o da un branch diverso da `main`; il via dell'utente non è verificabile dall'hook ed è una regola scritta. La pubblicazione del rilascio con `gh` richiede la GitHub CLI installata, come registrato nel `CLAUDE.md`. La pipeline di release si avvia solo dopo una domanda esplicita di conferma per ogni esecuzione (vedi «Integrazione GitHub»).

## Skill del plugin `kit` per commit e PR
Tre skill a lancio manuale applicano queste regole; il lancio da parte dell'utente è il via libera e le skill non chiedono altre conferme (restano la regola della domanda unica nei casi anomali e l'hook `guard-commands` attivo). **Prerequisito delle sole skill PR, verificato come primo passo:** la GitHub CLI è installata (`gh --version`) e autenticata (`gh auth status`); altrimenti la skill termina subito e dice cosa manca. I commit locali non richiedono `gh`:
- `/kit:commit-passo`: commit locali in sequenza e senza conferme intermedie, mai su `main` o `develop` (crea direttamente il branch di lavoro), piano in `piano-commit.md`; il tipo di commit si chiede solo se ambiguo, ci si ferma con una domanda solo nei casi anomali (vedi «Commit multipli»).
- `/kit:pr-develop`: PR da `feature/*` o `bugfix/*` verso `develop`, push e creazione senza altra conferma (titolo Conventional Commits, squash a cura dell'utente). Al termine di `/kit:commit-passo` Claude propone la PR con una sola domanda e, solo con il sì dell'utente, esegue la skill: è l'unica skill di PR che Claude può lanciare da sé (le altre skill che scrivono, committano, pubblicano o cancellano restano a lancio manuale).
- `/kit:pr-main`: PR da `develop` (o `release/*`, `hotfix/*`) verso il branch principale, push e creazione senza altra conferma; dopo il merge (confermato dall'utente ogni volta) pulizia dei branch di lavoro locali e remoti confermati e allineamento di `main` e `develop` con `git pull --ff-only`; con controllo di `main` avanti rispetto a `develop` e merge commit.
